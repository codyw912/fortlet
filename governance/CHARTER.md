# Operator Charter — First usable local Fortlet

Status: active. Issued 2026-08-10 by the operator.
Scope string for records created under it: `local-foundation/v1`.

This charter governs work toward a portable local Fortlet release that can
transparently launch supported coding-agent commands inside reliable
project-scoped capsules. It grants bounded autonomy: within the grants and
constraints below, no per-step operator sign-off is required. Violating a hard
invariant or hitting an escalation trigger suspends the charter until the
operator responds.

## Mission

The ONLY deliverable that counts is a local Fortlet workflow suitable for
ordinary daily agent use. Everything else — tooling, hardening, tests,
documentation — is instrumental and justified only insofar as it unblocks this.

## Definition of Done (falsifiable)

1. Registered harness commands launch transparently through Fortlet and preserve
   arguments, terminal behavior, current directory, signals, and exit status.
2. Failure to establish the declared isolation or credential boundary prevents
   the harness from starting and reports one actionable next step.
3. Codex and Tact work from independently provisioned, pinned Linux tool layers
   in project-and-harness capsules with concurrent attachment.
4. Capsule state, credentials, and broad-root handling meet FIP-0001 and have
   automated coverage.
5. The Rust binary and MicroSandbox runtime build reproducibly through Nix on
   every declared system.
6. The standard verification set is green; then STOP and report. Publication,
   remote execution, services, and a dashboard require successor charters.

## Autonomy Grants (no operator sign-off needed)

1. Spend: up to 20 hours of declared engineering effort, with no external money,
   paid quota, public remote mutation, or repository publication.
2. Design discretion: full discretion over implementation details within
   accepted FIPs and the constraints below.
3. Successor experiments: declare, implement, and run offline experiments with
   at most one in flight.
4. Local test capsules and disposable test state may be created and removed when
   their names are generated by Fortlet and their ownership is verified first.

## Hard Invariants

1. Provider secrets, SSH private keys, the 1Password SSH agent, and unrestricted
   publication credentials never become guest-readable or persist in capsules.
2. Fortlet never silently falls back to an unisolated harness launch.
3. Project mounts are canonicalized and broad roots are replaced with safe
   scratch space unless the user explicitly overrides the protection.
4. The host process never executes repository-controlled hooks or shell text at
   a future publication boundary.
5. No hosted control plane, required vendor account, telemetry, or registry
   login may be introduced.

## Direction Constraints

1. Preserve native harness UX; successful wrapper startup is silent.
2. Prefer disposable capsule roots plus explicit persistent paths over snapshot
   or configured-machine persistence.
3. Harness-specific behavior belongs in harness adapters, not conditional logic
   spread through orchestration.
4. Do not generalize for alternative runtimes or remote execution until a real
   implementation supplies requirements.
5. Add process only when a recorded blocker requires it.

## Escalation Triggers

1. Any external spend, remote push, PR creation, package publication, or public
   user test.
2. Two consecutive terminal failures that share an assumption.
3. Any need to weaken a hard invariant or change an accepted FIP.
4. Any anomaly suggesting credential exposure, data loss, unowned process
   termination, or mutation outside the project.

## Cadence

Report after every goal deliverable and experiment terminal closure: outcome,
root cause, effort total, and next action. More than one working day without a
verified deliverable is itself report-worthy.

## Context to Internalize

The Rust SDK path, interactive terminal attachment, shared same-harness capsule,
credential broker, and reproducible macOS package are already proven. The
remaining risk is day-to-day product integration—especially transparent shims,
lifecycle behavior, and failure UX—not another backend bake-off or more
packaging apparatus.
